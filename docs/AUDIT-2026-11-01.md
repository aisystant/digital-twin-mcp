**Как закрыты F1 и F7 — справкой шлюза.** Шлюз (`aisystant/gateway-mcp`) уже выпускает для своих серверов короткую справку: `mintGatewayAssertion` — RS256, `iss=iwe-gateway`, `aud=<сервер>`, `sub=<пользователь>`, `purpose=registry`, срок 60 секунд, ключи на `/gateway/.well-known/jwks.json`. Если серверу двойника задан `GATEWAY_JWKS_URL`, он принимает только эту справку в заголовке `X-Gateway-Assertion` (`aud=digital-twin-mcp`), берёт пользователя из неё и игнорирует токен Ory (`src/worker-sse.js:82–136`). Мимо шлюза справку не получить, а токен другого приложения ничего не значит — на любом адресе сервера. Без `GATEWAY_JWKS_URL` сервер работает по-старому и пишет предупреждение; `/health` показывает `gateway_assertion: "off" | "enforced"`.

**Изоляция данных между пользователями — проверено, утечки нет.** Все 6 запросов к базе привязаны к пользователю из проверенного токена или справки (`src/twin-store.js:71–91`), либо к `DT_USER_ID` в stdio (`src/index.js:401`), либо не вызываются (`checkSubscription`). Ни у одного инструмента нет аргумента, задающего пользователя; значения передаются параметрами `$n`.

## 2. Включение защиты (F1, F7)

**Выполнено 2026-11-01.** Шлюз переведён на справку (`aisystant/gateway-mcp#129`), серверу двойника задан `GATEWAY_JWKS_URL`. Проверено снаружи на обоих адресах: `/health` → `"enforced"`; токен без справки → 401 `gateway_assertion_required`; поддельная справка → 401 `invalid_gateway_assertion`; `tools/list` открыт; битый JSON → 400. Через шлюз из VS Code двойник читается свой. Не проверено: claude.ai и бот (живая проверка у пилота). Откат — удалить секрет `GATEWAY_JWKS_URL`. Ниже — порядок, по которому включали; он же нужен при переезде на новую инфраструктуру.

Слияние ветки для пользователей ничего не меняет. Порядок:

1. **Слить ветку.** Появляются запись `mcp_auth` в журнале и поле `gateway_assertion` в `/health`.
2. **Владелец шлюза** переключает двойника в `getBackends` (`src/index.ts:1041` шлюза) на `auth: "assertion", audience: "digital-twin-mcp"` и выкладывает шлюз. Шлюз продолжает пересылать и токен пользователя, поэтому этот шаг ничего не ломает. Значение `digital-twin-mcp` продолжает соглашение `checklist-mcp`; его нужно согласовать.
3. **Живая проверка** на одном пользователе из claude.ai, из бота и из VS Code: инструменты `dt_*` видны сразу после входа, `dt_read_digital_twin` возвращает своего двойника, а не пустого.
4. **Проверка прямых вызовов** — с двух сторон:
   - со стороны бота — **проверено 2026-11-01** по журналам рабочего и пилотного ботов в Railway (настройки не читались): с 20 октября при каждом запуске клиент двойника загружает 0 токенов, а в журнале адресов рабочего бота нет обращений ни к `twin.aisystant.com`, ни к адресу двойника на `workers.dev` (фильтр проверен на адресе, к которому бот точно ходит; журнал адресов охватывает только текущую выкладку, примерно сутки-двое). Вывод: бот напрямую к двойнику не ходит и включению не мешает; его клиент двойника — мёртвый код, удалить в боте, сначала в ветке `pilot`;
   - со стороны двойника: журнал `npx wrangler tail digital-twin-mcp --format json --search mcp_auth`. Сначала взять один заведомо известный вызов через шлюз и записать его значение `cf_worker`. Cloudflare ставит заголовок `CF-Worker` на запросы от **любого** воркера любого владельца, поэтому само наличие заголовка ничего не доказывает. Прямым вызовом считать всё, у чего `cf_worker` отличается от эталонного или пустой; поле `user_agent` помогает узнать клиента (бот написан на Python). Окно наблюдения — не длиннее срока хранения журналов на тарифе Cloudflare (3–7 дней), иначе начало окна пропадёт.
5. **Задать `GATEWAY_JWKS_URL`** (`wrangler secret put GATEWAY_JWKS_URL`), только когда прямых вызовов нет. Адрес по коду шлюза — `https://mcp.aisystant.com/gateway/.well-known/jwks.json`; перед этим открыть его и убедиться, что ключи там есть. `/health` → `"gateway_assertion":"enforced"`.
6. **Проверка после включения:** запрос по обоим адресам сервера (`workers.dev` и `twin.aisystant.com`) с одним токеном Ory → 401 `gateway_assertion_required`; вызов двойника через шлюз работает.
7. По желанию: посмотреть в Cloudflare `DIGITAL_TWIN_MCP_URL` шлюза; если там не `workers.dev`, выключить `workers.dev` как дополнительную защиту. До этого не выключать: в примере настроек шлюза указан именно `workers.dev`.

**Остаточные риски:**
- **Прямой клиент бота** — снят: проверка 2026-11-01 (шаг 4) показала 0 токенов и ни одного прямого вызова.
- **Идентификатор пользователя.** Шлюз кладёт в справку `sub` и для токена-JWT, и для непрозрачного токена через Hydra userinfo (`data.sub || data.user_id`); сервер раньше брал тот же `sub`. Расхождение возможно только в запасной ветке `user_id`. Подтверждается шагом 3.
- **Список инструментов без пользователя.** Шлюз выпускает справку только при известном пользователе и пропускает такие серверы при плановом прогреве списка — так уже работает сервер чек-листа. Подтверждается шагом 3.
- **Повтор справки** в пределах срока (60 секунд; сервер допускает возраст до 120 секунд на расхождение часов), учёта `jti` нет. Риск принят.
- До шага 5 `tools/list` с недействительным токеном получает 401 (раньше получал список).

## 4. Порча строк (F3) и миграция

**Перепись рабочей базы, 2026-11-01** (база `indicators`, таблица `public.digital_twins`, запрос ниже; выполнил пилот):
- `1_declarative`: строк, похожих на JSON, нет, кроме восьми полей `period` в `life_history` — это строки вроде года, они лежат строками и после #32 защищены. Типы совпадают с метамоделью там, где она задаёт тип (`19_Недельный бюджет времени`, `10_Планируемое время на завтра` — числа; `list[string]` — массивы; время и режимы — строки).
- Единственный след прежнего разбора — `1_3_selfeval/11_Срок обучения`: у 40 записей число (бот шлёт строку, сервер до #32 превращал её в число). Пути нет в метамодели, читателей нет; новые записи будут строкой, старые останутся числом. Это безвредно; исправление — в боте (слать число или писать в `1_5_delivery/03_Длительность занятия`).
- Прочие смешанные типы (одиночная строка вместо массива, `12_Текущие роли` в трёх видах) — старые данные, не результат разбора: в них нет строк, похожих на JSON.
- `2_collected` чист: сборщики пишут в базу напрямую, минуя разбор.

**Вывод: миграция старых данных не нужна.** Остаётся только поведение кода: разбор строки, похожей на объект или массив, при записи и при чтении.


**Две точки искажения:**
- **запись через HTTP** (`src/worker-sse.js:298–300`): записываемое значение верхнего уровня разбирается как JSON, если строка разбирается. `"42"` → число, `"true"` → логическое, `"null"` → пустое, `"[1, 2]"` → массив. Вложенные поля не трогаются. Это задуманное и описанное поведение (описание инструмента `write_digital_twin`), идёт с 15 февраля;
- **чтение** (оба сервера, `src/worker-sse.js:197`, `:290`; `src/index.js:84`, `:258`): строка, начинающаяся с `{` или `[`, отдаётся объектом.

Отмена разбора при записи — ломающее изменение для клиентов, которые на него рассчитывают: делать с предупреждением.

**Сделано 2026-11-01 (первый безопасный шаг).** Облачный сервер при записи разбирает только строку, в которой лежит JSON-объект или массив; остальные строки хранит как текст. Для клиентов, которые присылают структуру строкой, поведение не меняется; ломается только запись скалярных строк, и ни один известный писатель (бот, диагностика, синхронизатор) на неё не рассчитывает: бот присылает текстовые значения, диагностика присылает объект. Тесты: `src/write-value-decoding.test.js`. Остаётся: строка, которую пользователь написал как `[1, 2]`, всё ещё становится массивом, пока не задано сопоставление пути с показателем метамодели.

**Перепись (только чтение)** — какой тип фактически лежит по каждому пути, включая элементы массивов. Проверено на PostgreSQL 16; `pg_input_is_valid` есть с версии 16:

```sql
WITH RECURSIVE walk(path, value) AS (
  SELECT ARRAY[]::text[], data FROM digital_twins
  UNION ALL
  SELECT w.path || c.key, c.value
  FROM walk w CROSS JOIN LATERAL (
    SELECT key, value FROM jsonb_each(CASE WHEN jsonb_typeof(w.value) = 'object' THEN w.value END)
    UNION ALL
    SELECT '[]', value FROM jsonb_array_elements(CASE WHEN jsonb_typeof(w.value) = 'array' THEN w.value END)
  ) c
)
SELECT array_to_string(path, '.') AS path, jsonb_typeof(value) AS stored_type,
       count(*) FILTER (WHERE jsonb_typeof(value) = 'string'
                          AND pg_input_is_valid(value #>> '{}', 'jsonb')) AS json_looking_strings,
       count(*) AS n
FROM walk
GROUP BY 1, 2 ORDER BY 1, 2;
```

**Правило по типу поля в метамодели:**
1. Путь соответствует показателю с текстовым `Format` (`string`, `structured_text`, `enum`, `time`, `date`, `day_time`), а лежит число, логическое, пустое значение или объект — это след разбора при записи. Значение вернуть в строку. По оценке проверки моделью Fable, для 41 текстового поля из 106 это восстановимо (теряются только пробелы и запись чисел); безвозвратно неясны поля-объекты и пустые значения.
2. Путь с объектным `Format` (`object`, `structured_object`, `list[string]`, `list[object]`, `checklist`), а лежит строка, похожая на JSON, — старая запись объекта строкой. Разобрать в JSON.
3. Пути, которых нет в метамодели (например, `3_derived.rcs_profile`), автоматически не трогать: выгрузить и решить по каждому.
4. Перед миграцией — полная копия таблицы. Эвристику чтения удалять только после миграции и прохождения теста F3.

Сопоставление путей данных с файлами метамодели в коде не задано — вопрос В3.
