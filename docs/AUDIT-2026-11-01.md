Проверка получателя и общий секрет включаются секретами, а не кодом. Иначе выкладка, которая идёт автоматически при слиянии в основную ветку, отрезала бы шлюз раньше, чем он научится посылать заголовок. Пока секреты не заданы, сервер пишет в журнал предупреждение, а дыры остаются открытыми. **Исключение — выключение `workers.dev`:** оно записано в `wrangler.toml` и срабатывает сразу при слиянии, независимо от секретов.

> **Пересмотр (отзыв по коду шлюза, 2026-11-01).** Обе схемы из этой версии, скорее всего, не нужны и включать их не следует. (1) Шлюз входит в Ory под единственным своим приложением и не запрашивает получателя, поэтому поле `aud` в токенах, вероятно, пустое, и любое значение `JWT_AUDIENCE` отсечёт все запросы; перед включением нужно разобрать нагрузку настоящего токена. (2) У шлюза уже есть подписанная им короткая справка «кто пользователь и для какого сервера», которая по умолчанию стоит у новых серверов; сервер двойника остался на пересылке токена пользователя. Переход на справку закрывает F1 и F7 сразу, без третьей схемы доверия. Решение — за пилотом и владельцем шлюза; код шлюза в этой среде недоступен, выводы отзыва здесь не проверены.

**Порядок выкладки:**

1. Посмотреть в Cloudflare значение настройки шлюза `DIGITAL_TWIN_MCP_URL`. Если там адрес `workers.dev` — сначала перевести шлюз на `twin.aisystant.com`, иначе слияние отрежет доступ.
2. Узнать `aud` токенов, которые шлюз пересылает, и задать его: `wrangler secret put JWT_AUDIENCE`.
3. Научить шлюз посылать `X-Gateway-Secret`, затем задать тот же секрет серверу: `wrangler secret put GATEWAY_SHARED_SECRET`.
4. Слить ветку — выкладка автоматическая.
5. Проверить командами из §3: без секрета шлюза ответ 403.

**Изменение поведения:** `tools/list` публичен только без заголовка `Authorization`. С недействительным токеном теперь ответ 401 (раньше список отдавался).

**Поправки после проверки моделью Fable:**

- **Порча данных шире и уже одновременно.** При записи через HTTP разбирается только само записываемое значение верхнего уровня, вложенные поля не трогаются. Зато портятся не только `{` и `[`: `"42"` становится числом, `"true"` — логическим значением, `"null"` — пустым значением. Запрос переписи из §4 таких случаев не находит и пропускает строки внутри массивов — его нужно переделать.
- **«Необратимо» было завышено.** По оценке проверки, для 41 текстового поля из 106 значение восстановимо (теряются только пробелы и запись чисел); безвозвратно неясны поля-объекты и пустые значения.
- **Разбор строк при записи задуман и описан** в описании инструмента. Его отмена — ломающее изменение для клиентов, делать с предупреждением, а не правкой за час. Порча идёт с 15 февраля.
- **Шаблон не только читает двойника:** диагностика пишет в него, генератор руководства вызывает описание метамодели. Удалению локального сервера это не мешает: его никто не запускает.
- **Неуправляемая запись синхронизатора не подтвердилась:** сравнение всего документа и повтор при конфликте сохраняют обе записи. Открыт вопрос В7: пишут ли все четыре участника (облачный сервер, локальный синхронизатор, диагностика, сборщик профиля на tsekh-1) в одну схему базы.
- **Новое:** битый запрос валил сервер до проверки токена, то есть это мог сделать кто угодно — исправлено (F4).

## 2. Находки

| № | Находка | Важность | Где | Тест |
|---|---|---|---|---|
| F1 | Принимается токен, выпущенный другому клиенту Ory | **критический** | `src/worker-sse.js:35` | да |
| F7 | Сервер доступен напрямую, в обход шлюза с проверкой подписки | **критический** (если подтвердится) | `wrangler.toml:4`, `:6–8` | нет, инфраструктура — §3 |
| F2 | stdio `describe_by_path` читает файлы вне каталога метамодели | **высокий** | `src/index.js:185` | да |
| F3 | Строки пользователя превращаются в массивы/объекты (ошибка целостности данных) | **высокий** | `src/index.js:84`, `:258`; `src/worker-sse.js:102`, `:195`, `:203–206` | да (stdio) |
| F4 | Битый JSON роняет облачный сервер | **средний** | `src/worker-sse.js:328` | да |
| F5 | `tools/call` без `params` роняет облачный сервер | **средний** | `src/worker-sse.js:243` | да |
| F6 | Начало `DATABASE_URL` пишется в журнал на каждом запросе | **средний** | `src/worker-sse.js:291` | да |
| F8 | На уведомление сервер отвечает телом ошибки вместо 202 | **низкий** (исчезает при переходе, см. §5) | `src/worker-sse.js:226` | да |
| F9 | Нет лимита размера тела запроса и частоты вызовов | **средний** | весь обработчик | нет: сначала решить значение лимита |

**F1 — почему критический, хотя изоляция в порядке.** Атакует не другой пользователь, а стороннее приложение от имени того же человека. Пользователь входит через Ory в любое другое приложение того же проекта Ory. Это приложение получает его токен и с ним читает и переписывает его цифрового двойника: сервер проверяет подпись и издателя, но не получателя (`aud`). Насколько это реально сейчас, зависит от того, сколько клиентов выпускают токены в этом проекте Ory — открытый вопрос В1.

**F3 — две точки искажения.** При чтении оба сервера превращают строку, начинающуюся с `{` или `[`, в объект. Облачный сервер дополнительно делает это при записи (`src/worker-sse.js:203–206`): строка пользователя `"[1, 2]"`, записанная через HTTP, сохраняется в базу уже массивом. Значит, часть данных в базе исказилась необратимо, и миграция должна это учитывать (§4).

**F2 — исправление полностью:** разрешить путь через `fs.realpath` (с учётом символических ссылок) и проверить, что результат равен корню метамодели или начинается с `корень + path.sep`. Риск реален, когда у модели есть канал вывести прочитанное наружу; у агента с доступом в сеть он есть почти всегда.

Понижено до **низкого**: CORS `*` (авторизация токеном в заголовке, без куки), чтение по пути `constructor` (портит ответ, данных не раскрывает).

## 3. Проверка обхода шлюза (F7) — для обоих адресов

У сервера два публичных адреса: `workers.dev` (`wrangler.toml:4`) и маршрут `twin.aisystant.com/*` (`wrangler.toml:6–8`). Если шлюз работает на другом адресе, оба идут мимо него. Проверка с токеном пользователя **без подписки** (синтетическая учётная запись, только чтение):

```bash
curl -s -X POST "https://digital-twin-mcp.<аккаунт>.workers.dev/mcp" -H "Authorization: Bearer $TOKEN_NO_SUB" -H 'Content-Type: application/json' --data '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"read_digital_twin","arguments":{"path":"/"}}}'
```

```bash
curl -s -X POST "https://twin.aisystant.com/mcp" -H "Authorization: Bearer $TOKEN_NO_SUB" -H 'Content-Type: application/json' --data '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"read_digital_twin","arguments":{"path":"/"}}}'
```

Ответ с данными (не `Unauthorized`) — обход подтверждён. Исправление: выключить `workers_dev`, а запросы на маршрут принимать только от шлюза (привязка сервисов или общий секрет со шлюзом). Проверку подписки в сервер не возвращать — по замыслу её делает шлюз.

## 4. Миграция строковых данных (для F3)

По старому значению нельзя отличить «объект, сохранённый строкой» от «так написал пользователь». Правило:

1. **Перепись (только чтение)** — какие пути содержат строки, похожие на JSON:
   ```sql
   WITH RECURSIVE walk(user_id, path, value) AS (
     SELECT user_id, ARRAY[]::text[], data FROM digital_twins
     UNION ALL
     SELECT w.user_id, w.path || e.key, e.value
     FROM walk w, jsonb_each(w.value) e WHERE jsonb_typeof(w.value) = 'object'
   )
   SELECT array_to_string(path, '.') AS path, count(*) AS n
   FROM walk
   WHERE jsonb_typeof(value) = 'string' AND (value #>> '{}') ~ '^[\[{]'
   GROUP BY 1 ORDER BY n DESC;
   ```
2. **Решение по типу поля в метамодели.** Путь соответствует показателю с `Format` = `object`, `structured_object`, `list[string]`, `list[object]`, `checklist` → разобрать строку в JSON. `Format` = `string`, `structured_text`, `enum`, `time`, `date`, `day_time` → оставить строкой.
3. **Пути, которых нет в метамодели** (например, `3_derived.rcs_profile`), не трогать автоматически: выгрузить список и решить по каждому вручную.
4. Перед миграцией — полная копия таблицы. Удалять эвристику из кода только после миграции и прохождения теста F3.
5. Значения, которые HTTP-запись уже превратила из строки в массив, восстановить нельзя: исходной строки в базе нет. Это фиксируется как известная потеря, а не чинится.

Сопоставление путей данных с файлами метамодели в коде не задано (имена файлов вида `02_Имя`, ключи данных — свободные). Его нужно определить до шага 2 — открытый вопрос В4.

## 5. Переход на спецификацию MCP 2026-07-28 — ломающее изменение

Сервер говорит на версии `2024-11-05` (`src/worker-sse.js:235`). С тех пор вышли четыре редакции: 2025-03-26, 2025-06-18, 2025-11-25, 2026-07-28. Что меняет 2026-07-28 (по официальному списку изменений):

- рукопожатие `initialize` и уведомление `notifications/initialized` удалены; версия протокола и возможности клиента передаются в `_meta` каждого запроса; несовпадение версии → `UnsupportedProtocolVersionError`;
- обязателен вызов `server/discover`;
- сеансы и заголовок `Mcp-Session-Id` убраны;
- у каждого результата обязательное поле `resultType`;
- у HTTP-запросов обязательные заголовки `Mcp-Method` и `Mcp-Name`.

Если сервер перейдёт только на новую версию, а шлюз и клиенты останутся на старых, доступ к двойнику сломается у всех. Поэтому сервер должен какое-то время понимать обе версии.

**Поддержка в SDK (проверено по пакетам npm 2026-11-01):** SDK v1 `@modelcontextprotocol/sdk` 1.32.2 знает версии до 2025-11-25 и новую не поддерживает. SDK v2 `@modelcontextprotocol/server` 2.4.0 (2026-10-23) содержит и 2026-07-28, и прежние версии, плюс обработчик на веб-стандартах (`createMcpHandler`, `WebStandardStreamableHTTPServerTransport`), который работает и в Cloudflare, и на обычном Node. Это и путь к двойной поддержке версий, и путь к переносимости для передачи. Работу двойной поддержки нужно подтвердить прототипом.

F8 после перехода исчезает сама: уведомлений в новой версии нет. Отдельно её чинить стоит, только если старые версии будут обслуживаться долго.
